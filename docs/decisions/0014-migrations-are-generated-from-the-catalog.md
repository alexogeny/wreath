# 0014. Migrations are generated from the live catalog, not authored

Date: 2026-07-27
Status: Accepted
Absorbs: the retired `keep fixed and named migration representations separate`
record, whose four-image split survives intact.

## Context

Alembic-style migrations are authored files, ordered by a revision chain. Two
problems follow. The chain is a shared mutable sequence, so concurrent branches
conflict on ordering rather than on content. And the files describe an intent,
while the database holds a fact — drift between them is invisible until an
apply fails.

Wreath's ORM already declares the schema. The catalog already knows what exists.
The difference between them is computable.

## Decision

Migrations are **generated by diffing the declared schema against the live
catalog**, not authored. `wreath migrations detect/check/generate/show/status/apply`
drives it, with a first-class inverse `down` derived in metal from the same
artifact.

The representation is deliberately split into four images bound in one
authoritative artifact:

- **WMI1** — compact, fixed-width schema resolution. No string materialisation,
  for the hot resolver and the fleet runner.
- **WMO1** — metal-derived operations.
- **WMP1** — literal PostgreSQL names and full before/after signatures.
- **WMS1** — the SQL statements.

The hot path needs fixed-width records with no strings; generation, review SQL,
diagnostics and approval need literal names and signatures. Expanding every
record with strings would tax every tenant; discarding names would make safe
review and SQL generation impossible.

## Consequences

- There is no revision chain to conflict on. Two branches that touch different
  tables produce artifacts that do not collide.
- Drift is detectable by construction, because detection and generation are the
  same computation.
- One artifact, one transaction, advisory-locked, with source and target
  fingerprints verified against the catalog on **both** sides.
- What the generator cannot express must be said out loud rather than
  approximated. Composite constraints, full FK actions, and expression indexes
  are documented as MANUAL, and `docs/from-fastapi/alembic.md` says to keep
  Alembic for exactly those.
- The generator's own ordering is a correctness surface: it shipped unable to
  apply its own artifact because foreign keys were emitted before the tables they
  referenced. The fix is pinned by a test asserting the *property* — FKs last —
  rather than the symptom.

## Alternatives rejected

- **Authored migrations with autogenerate.** Rejected: autogenerate produces a
  draft a human edits, so the file and the diff diverge from the first edit, and
  the file wins.
- **Declarative-only, no artifact.** Rejected: applying a diff computed at deploy
  time gives no reviewable object and no fingerprint to verify against.
- **One combined representation.** Rejected on cost — see the four-image split
  above; this is the reasoning the retired record contributed.

## What would reverse this

A schema change class that is genuinely uninferrable from a declaration *and*
common enough to matter. The MANUAL list is that class today; if it grew to
cover ordinary work, authored migrations would be the honest answer.
