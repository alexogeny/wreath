# v0.1.0a3

_Released 2026-07-28._

The first release you can actually follow the quickstart with. v0.1.0a2 installed
cleanly and then failed on the next line: `wreath run app:app` could not import
`app`, and on the paths where it did start, the server printed nothing at all, so
a working boot was indistinguishable from a hang.

## Added

- `wreath.server.run()` takes a `ready` callback, invoked once with the running
  `Server` after every listener is bound and lifespan startup has finished, and
  before the first request is accepted. It fires after the bind so a `port=0`
  listener already knows its port and a failed bind never announces itself; an
  exception from the hook tears the server down rather than leaving a bound
  listener behind something nobody saw fail.

## Fixed

- **`wreath run app:app` now imports `app.py` from the directory you are standing
  in.** A console script starts with `sys.path[0]` pointing at the virtualenv's
  `bin`, not the working directory, so the command the README and the
  getting-started guide both open with failed on a fresh install with
  `No module named 'app'`. `run` now prepends the working directory the way
  `python -m` does, and leaves `sys.path` alone when a caller already arranged
  for it. `wreath dev` was never affected — it re-executes `python -m wreath`,
  and that inconsistency is what made this a defect in `run`.
- **`wreath run` prints a startup line.** One line naming the version, the
  target, the bound `scheme://host:port`, the protocols, whether requests are
  served by the native extensions, the loop, and the
  worker count when there is more than one. The address comes from the bound
  socket rather than the configuration, so `--port 0` reports the port the kernel
  actually assigned; the tier is read from the same selector the server uses, so
  a process that fell back to pure Python cannot claim `native`. Under
  `--workers N` the supervisor prints once, after every worker signals ready,
  instead of N times.

## Docs & internals

- The quickstart path is covered by a test that drives the installed console
  script in a subprocess with `PYTHONPATH` scrubbed, and asserts on a served
  response rather than a clean start. In-process tests and `python -m wreath`
  both pass with the fix reverted, which is why neither is used there.
